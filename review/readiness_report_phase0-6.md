# Frontend Readiness & Integration Report

**Verdict:** `not ready`
The frontend components are largely well-implemented, dynamically integrated, and respect the "no numerical clutter" and animation guidelines for the canvas. However, two blockers prevent closure: a violation of the strict "NO mockdata" requirement in the sandbox, and a violation of the repository hygiene rules regarding `.gitignore` exceptions for large binary weights.

## Blockers

1. **Mock Data Synthesizing Real Pipelines**
   - **ID:** `FRONTEND-001`
   - **Severity:** Blocker
   - **Location:** `app/views/sandbox.py`, Lines 54-82
   - **What's wrong:** The preset shock scenarios actively generate stochastic synthetic sequences (using `np.zeros`, `np.linspace`, and `np.random.normal`) rather than utilizing real dataset records with applied perturbations. This directly violates the rule against using test tautologies or mock data to simulate real pipelines.
   - **Evidence:** 
     ```python
     seq = np.zeros((Config.SEQ_LEN, Config.NUM_INPUT_FEATURES), dtype=np.float32)
     base_line = np.linspace(0.2, 0.35, Config.SEQ_LEN)
     ...
     noise = np.random.normal(0.0, 0.03, Config.SEQ_LEN)
     ```
   - **Suggested Fix:** Replace the synthetic data generators with random samples pulled from the real historical test partition, injecting shocks/spikes directly into the real baseline data.

2. **Gitignore Rule Violation**
   - **ID:** `FRONTEND-002`
   - **Severity:** Blocker
   - **Location:** `.gitignore`, Line 14
   - **What's wrong:** The repository hygiene rule strictly states that "Large binary model weights (`outputs/models/*.pt`) remain git-ignored to prevent repository bloat". However, the `.gitignore` file includes an explicit whitelisting override `!outputs/models/*.pt`.
   - **Evidence:** Line 14 of `.gitignore` is `!outputs/models/*.pt`.
   - **Suggested Fix:** Remove the `!outputs/models/*.pt` line from the `.gitignore` file to ensure binary weight files are properly ignored.

## Unverified Suspicions
- **Cross-page State Navigation:** The dynamic navigation routing from the Monitor to the Diagnostic XAI page (via `st.session_state["page_why"]`) relies on Streamlit's new `st.navigation` framework. While statically sound, its runtime behavior handling the `selected_node_idx` index transfer hasn't been actively validated through E2E interactive testing.

## Things Verified as Working
- **SVG Canvas Component (`app/ui/canvas.py`):** The recent design iterations are fully intact. 
  - **Animations:** The `sg-float-node` classes provide ambient floating animations. The `sg-critical-glow`, `sg-disrupt-ripple-1`, and `sg-disrupt-ripple-2` animations strictly enforce the 1.0s delay requirement.
  - **Zero Numbers:** The visualization properly uses qualitative textual states (`NOMINAL`, `IMPACTED`, `DISRUPTED`, `CASCADE ▶`) and visual styling for data telemetry, without printing raw risk index values in the graph layout.
- **Dynamic Data Integrity:** `app/views/monitor.py` and `app/views/export.py` correctly implement actual predictive calls to the model (`predict_window`) using sequences generated by `get_test_windows()` without hardcoded fallback placeholders. Missing dataset states are handled correctly via the `empty_state` UI component.
- **Shell Restrictions:** No powershell commands or chained `&&` logic are dynamically created or executed within the Streamlit views.

## Open Questions
- What should be the default test window used by the Export page if no active `window_idx` has been defined prior to navigation? It currently defaults to `window_idx = 0`, but an explicit prompt might be better.
- Should the `tab_preset` sandbox feature be retained long-term if it requires real data sampling, or should it be merged with the `tab_upload` CSV feature for a purely user-provided sandbox experience?
